# ADR-0001：技术栈与公共层归属决策

- 状态：已接受
- 日期：2026-10-19
- 决策者：项目组（雏形阶段由搭建方提出，待组内确认）

## 背景

任务书要求"技术栈自选，建议选择企业级方案"，且每个项目组内分为至少 3 个模块组（M1/M2/M3），公共层 D 的归属由项目组自行决定，须形成书面决策记录。

## 决策

### 1. 技术栈

- **后端**：NestJS + TypeScript + TypeORM
  - 模块化架构天然对应 M1/M2/M3/D 的模块划分，便于三个模块组并行开发。
  - TypeScript 静态类型有助于接口契约治理与 AI 协作。
  - TypeORM 提供版本化迁移、多数据库支持（SQLite 开发 / PostgreSQL 生产）。
- **前端**：Vue 3 + Vite + Element Plus + Pinia + Vue Router
  - 中文生态最成熟的管理后台组合，组件覆盖预约/审批/工单类界面。
- **数据库**：PostgreSQL（生产）/ SQLite（开发默认）
  - 开发环境零配置可运行（本机无 Docker/PostgreSQL），`DB_TYPE` 一行切换，迁移脚本跨库兼容（避免 PG 专有类型）。
- **认证**：JWT + RBAC。

### 2. 公共层 D 归属方案：**拆分子域，由 M1 组牵头维护核心，M2/M3 组各自承担相邻子域**

| 子域 | 归属 |
|------|------|
| RBAC 身份与权限 | M1 组（自研需求最重，天然需要权限模型） |
| 空间与座位主数据 | M1 组（座位预约核心依赖） |
| 通知服务 | M2 组（审批通知最频繁） |
| 操作审计 | M3 组（工单流转操作密集） |

**考虑的因素**：
- 工作量均衡：M1 需求最详细（附件 1），主数据域与其强相关，由其牵头最自然；通知与审批（M2）、审计与工单流转（M3）同属一个业务闭环。
- 契约治理：公共层以明确接口（Service 公开方法）暴露，模块间通过接口调用，禁止直连数据库，降低耦合。
- 故障责任归属：每个子域有明确 owner，故障可追溯。

**达成一致的方式**：本项目雏形先按上述方案搭建公共层接口，正式分组后由各模块组在第一次 Review 前确认或调整，并以本 ADR 更新记录。

## 备选方案与放弃理由

- 公共层整体由单一模块组承担：该组工作量过载，且形成单点瓶颈，放弃。
- 使用微服务拆分 M1/M2/M3：任务书要求"组内各模块共享一套环境"，微服务治理成本超出课程范围，雏形采用单体应用 + 模块边界 + 内部接口调用的方式，保留后续拆分能力（模块间经 Service 接口调用，天然支持抽取独立服务）。
