# ADR-0006：M3 三期（挂起 / 合并 / 统计）的关键决策

- 状态：已实施
- 日期：2026-10-28
- 决策者：M3 组（k）
- 关联：`docs/m3/02-需求规格.md`（M3-14 / M3-15 / M3-17 / M3-18）、`docs/m3/04-开发记录.md`（S6）、ADR-0005
- 影响范围：`work_orders` 表结构（+13 列）、`WorkOrdersService` 状态机、D 层 `StatsView`

## 背景

二期（M3-19 ~ M3-31）补齐了协作与副作用处置，但 `docs/m3/02-需求规格.md` 的 M3-14 / M3-15 / M3-17 / M3-18 一直停在「已定义、未实现」。这四项不是简单加字段就能收尾，每一处都涉及口径或权限的取舍，需要先把判断写下来，否则实现出来的是一个能跑但结论不可信的系统。

## 决策

### 决策 1：挂起做成两级（维修员申请 → 派单员确认），不做一键暂停

- **理由**：挂起的实质是「暂停 SLA 考核」。若维修员一按按钮就停表，SLA 制度立刻退化为自证豁免——遇到难修的单一律挂起，报表永远漂亮。把确认权交给派单员，等于给暂停加了一道人为闸门。
- **代价**：多一次交互，多 4 个字段（`holdRequested` / `holdRequestedAt` / `holdRequestedBy` / `holdReason`）与一个待办列表。
- **配套**：申请阶段状态与 `slaDeadline` **均不变**（测试中有显式断言），确认后才置 `on_hold`。

### 决策 2：恢复时「平移」时限，不重算

- **实现**：`slaDeadline`、`responseDeadline`、`originalSlaDeadline` 三者同时 `+ 挂起时长`。
- **理由**：重算（`now + 原始小时数`）会凭空多出一段工期——挂起一次反而获得更宽裕的时限，属于反向激励。平移的语义是「时钟暂停」，恢复后剩余时间与挂起前完全一致。
- **`responseDeadline` 也平移**的原因：`dispatched` 状态下即可申请挂起，此时首响可能尚未发生，不平移会让维修员在恢复后立刻背负首响超时。

### 决策 3：新增 `originalSlaDeadline`，与 `slaDeadline` 分离

- **背景**：既有 `escalateOverdue` 每次升级都会把 `slaDeadline` 推后 `WORKORDER_ESCALATE_HOURS`（供下一轮催促使用）。若直接拿它计算 SLA 达标率，**任何被升级过的工单都会显示「未超时」**，达标率系统性虚高。
- **决策**：上报时写入同一时刻的两个值；`slaDeadline` 可被升级推后，`originalSlaDeadline` 只随挂起平移，永不参与催促。
- **代价**：一份冗余数据。
- **收益**：统计口径第一次做到自洽，且不需要回溯改写历史升级逻辑。

### 决策 4：合并只做「检出 + 建议」，绝不自动合并

- **理由**：「同房间另一个座位也坏了」与「同一座位被重复上报」在数据上几乎同形。自动合并判错的代价是把真实故障吞掉，且无人察觉；判不合并的代价只是多派一次工。
- **上报路径**：判重返回 `409` 并**附带 `existingWorkOrderId` / `existingWorkOrderNo`**，前端据此给出「合并到该工单」这一条出路——只堵不疏，用户会反复提交或放弃报修。
- **合并单的副作用**：落为 `merged`，`slaDeadline = null`（不承担独立工期），**不触发任何座位下架**（座位并集并入主线，恢复责任归主线）。
- **事后合并（`POST /:id/merge`）**：被合并单**清空自己的 `seatIds`**。若不清空，它被取消或验收时会把自己名下那部分座位提前放回可预约池，而主线还在修——这是合并最容易埋的坑。
- **已知取舍**：合并单若涉及主线未覆盖的座位（正常不会发生，因为真重复必然座位有交集），按「座位状态不变」的验收标准不下架，转而发通知提醒派单员人工下架。宁可漏一手也不悄悄改动座位状态。

### 决策 5：完工维修说明强制必填（破坏性变更）

- **理由**：报修人验收时若只看到「已修好」，既无法判断问题是否真的解决，事后也无据可查。强制写明「换了什么、为什么坏、后续注意什么」，验收才有意义。
- **代价**：`complete()` 签名变更，所有既有调用点必须同步改（本次同步修改了 3 个测试文件共 18 处调用）。属于**前后端必须同时上线**的变更。
- **放宽项**：照片仍为可选，完工时可补传，与上报时照片合并后仍受 `WORKORDER_MAX_PHOTOS`（3 张）约束。

### 决策 6：统计口径写进接口返回体，而不是只写进文档

- **决策**：`GET /stats` 返回 `definitions` 字段，逐条说明每个比率的分母。
- **理由**：同一份数据换个分母就能得出相反结论（完工率算不算取消单，能差出十几个百分点）。口径只写在文档里，前端迟早各写各的；随数据返回，界面直接展示，评审时也无从含糊。
- **三条具体口径**：
  1. 完工率分母 = `total − cancelled − merged`（取消与合并不是「没修好」，计入分母等于惩罚合理操作）；
  2. 平均解决时长扣 `totalHoldMinutes`（挂起是客观停工，算进作业效率会让「等两周配件」看起来像维修员手慢）；
  3. SLA 达标率用 `originalSlaDeadline` 判定（见决策 3）。

## 后果

- `work_orders` 增加 13 列，由迁移 `1780000003000-m3-hold-merge-stats` 一次性补齐，全部 `ADD COLUMN`，SQLite 与 PostgreSQL 双库兼容。
- 新增 2 个 SQLite 无法回滚的索引（`mergedIntoId`、`createdAt`），`down` 用 `DROP INDEX IF EXISTS` + 逐列 `try/catch`。
- 状态机从 6 态扩到 8 态（`on_hold` / `merged`），前端 4 个页面的 `statusMap` 必须同步，漏一处会渲染出 `undefined`。
- 测试基线由 6 套件 56 条升至 **7 套件 75 条**；按 NFR-05 注入 3 处缺陷验证，恰好 3 条测试变红，确认断言真实有效。另有 1 条为定时任务幂等的回归测试（见 04-开发记录 S6「首响超时每轮重复升级」）。

## 未采纳的方案

| 方案 | 否决原因 |
|---|---|
| 挂起一键生效，事后审计 | SLA 考核形同虚设，审计只能事后追责，无法阻止规避 |
| 恢复时按「剩余比例」重算时限 | 实现复杂且仍多出工期，收益不抵风险 |
| 用 `slaDeadline` 直接算达标率 | 升级过的工单全部失真，见决策 3 |
| 上报时按空间+分类自动合并 | 会吞掉真实故障，无人察觉 |
| 合并单也单独下架座位 | 违反「合并不产生新副作用」的验收标准，且与主线恢复逻辑打架 |
| 把维修说明做成「建议填写」 | 无约束等于没有，二期已证明可选字段最终都是空的 |
