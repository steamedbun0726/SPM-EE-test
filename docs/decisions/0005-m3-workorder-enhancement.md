# ADR-0005：M3 报修工单增强方案的关键决策

- 状态：提议（待组内评审）
- 日期：2026-10-27
- 决策者：M3 组（k）
- 关联：`docs/m3/01-开源调研.md`、`docs/m3/02-需求规格.md`、`docs/m3/03-改造方案.md`
- 依赖：ADR-0002（座位可用性模型）、ADR-0004（公共层归属）—— 均出自 M2 组 PR #1，尚未合并

## 编号说明

本 ADR 编号从 0002 跳至 0005。原因：M2 组已于 PR #1（`feat/m2-adr-baseline`，2026-10-21）占用 0002 / 0003 / 0004 三个编号（座位可用性模型、教室预约流程、公共层归属），且提出时间早于本文。为避免合并后编号重复引用混乱，M3 侧主动让号，取当前最大编号 +1。今后新增 ADR 按合并顺序取号，冲突时后来者让号。

## 背景

M3 模块在雏形阶段已实现「上报→派单→开工→完工→验收」主干流程与座位下架/恢复联动，测试通过。但对照 `docs/requirements.md` 的验收要求（可追溯、跨模块写回、超时升级）与开源项目实践，存在四处结构性缺口：

1. 座位联动只到「房间」粒度，单座位报修不生效；
2. 状态流转无留痕，改派/返工/挂起等常见动作没有路径；
3. SLA 只有单一解决时限，无法考核接单速度，也不支持挂起暂停；
4. 超时升级只累加计数，没有实质处置。

## 决策

### 决策 1：不引入开源系统，按「借鉴模式、自研实现」推进

- **理由**：无 NestJS + TypeORM 同栈实现；现有开源项目（zammad 6038★、osTicket 3994★、frappe/helpdesk 3450★）体量为数十万行，无法在课程周期内消化；核心考点「维修中下架座位」强依赖本校 `SeatStateService`，外部系统不可能具备。
- **代价**：需要自己设计与实现，工作量大于套壳。
- **收益**：过程可自证，符合课程「软件过程管理」的考核导向。

### 决策 2：新增 `WorkOrderEvent` 事件表作为唯一留痕载体

- **理由**：现有 4 个时间戳字段无法表达改派、返工、挂起等动作；审计日志只记录 HTTP 层，不含业务状态变化。事件表可同时满足展示（时间线）与审计（追溯）两个诉求。
- **备选与放弃**：① 继续加时间戳字段——字段膨胀且无法记录同一动作多次发生（如两次返工）；② 引入完整事件溯源（Event Sourcing）——过重，课程项目不需要重放重建状态。
- **约束**：事件只追加不修改；所有状态变更收敛到 Service 内的单一私有方法写入，禁止在 Controller 直接改状态。

### 决策 3：座位下架/恢复增加「座位粒度」，以新增方法实现而非改造既有方法

- **理由**：既有 `setMaintenance(spaceId, ...)` 被 M3 现网逻辑与测试依赖，直接改签名会破坏契约。新增 `setSeatMaintenance(seatId, ...)` / `restoreSeatAfterMaintenance(seatId, ...)`，内部复用同一套 `apply()` 与 `SeatStatusLog` 写入，保证来源标记一致。
- **影响面**：属公共层变更。按 ADR-0004 的子域划分，`SeatStateService` 归 D2「空间与座位主数据」，owner 为 M1 组，需其确认方法签名。

#### 与 M2 组 ADR-0002 的对齐

M2 组 ADR-0002 提出把 `Seat` 的「物理状态」与「时段占用」分离：占用写入新的 `occupancies` 表，`SeatStateService` 收缩为「只处理物理状态（维修上下架）」。该 ADR 第 5 节明确写着 **「M3：不变」**，并把「M3 维修是否需要时段化」列为遗留问题、v1 不做。

本文决策 3 与该方向完全兼容，且是其落地的必要补充：

| 本 ADR | 与 ADR-0002 的关系 |
|---|---|
| 座位粒度维修下架写 `Seat.status='maintenance'` | 一致：维修是物理状态，不写 `occupancies` |
| 新增 `setSeatMaintenance` / `restoreSeatAfterMaintenance` | 补充：ADR-0002 只把 `SeatStateService` 收缩到物理状态，未定义座位粒度入口 |
| 挂起（`on_hold`）期间座位保持下架 | 一致：物理损坏未修复，不应因流程挂起而恢复可约 |

**结论**：M3 不消费 `OccupancyService`，只依赖 `SeatStateService`；两方在 `Seat.status` 上的写权限归 D2，M3 通过方法调用而非直接改表。

### 决策 4：返工不新增状态，复用 `in_progress` + `reopenCount` 计数

- **理由**：新增 `reopened` 状态会让前端分支、统计口径、定时任务条件全部多一套，收益仅是语义更直白。用计数字段即可支撑「返工率」统计与「最大返工次数」约束。
- **代价**：需要看 `reopenCount` 才知道这是第几轮，查询时需额外字段。

### 决策 5：保留 `slaDeadline` 语义，新增 `responseDeadline` 而非重命名

- **理由**：`slaDeadline` 已被既有测试与前端引用，重命名会同步波及 M1/M2 无关代码。将其语义固定为「解决时限」，新增「首响时限」字段，向前兼容。
- **挂起顺延**：挂起恢复时把 `slaDeadline` 顺延 `totalHoldMinutes`，历史数据无需回填。

### 决策 6：重复工单不自动合并，必须显式指定合并目标

- **理由**：自动合并的判定（同房间？同分类？时间窗？）容易误判，把两起独立故障（如「灯坏了」和「空调坏了」）错并为一张，反而丢失信息。改为上报时检测冲突并提示，由人决定是否合并。

## 后果

- **正面**：流程闭环、可追溯性满足验收要求；一期（P0）可独立交付，不影响 M1/M2。
- **负面**：单表字段增加到 20+，需要清晰的实体注释；事件表带来额外写入，性能影响可忽略（课程规模）。
- **需要同步的事项**：`docs/requirements.md` 的 M3 章节需在一期完成后追加新需求条目；`docs/backend-contracts.md` 的 M3 接口章节需随接口新增更新；种子数据需补 4 个权限码与 3 个配置项。
