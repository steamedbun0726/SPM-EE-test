# ADR-0003：整教室预约的状态机与审批规则

- 状态：提议（待组内评审）
- 日期：2026-10-21
- 提出：M2 组
- 上游：ADR-0002（座位可用性模型）已确定「占用」如何表达；本 ADR 确定「申请」如何流转
- 前置：脚手架中的 M2 实现视为原型，本 ADR 按需求重新定义，不沿用其隐含规则

## 1. 背景

任务书对 M2 只给了四个词：**权限门槛、申请提交、多级审批（通过／驳回）、超时自动撤销**。其余全部要自己定义，且「M2 和 M3 和 D 根据自己理解，通过与 AI 交互完成细化的需求」。

脚手架实现里存在几处未定义或自相矛盾的地方：

- 需求写「非学生可申请」，但种子数据给学生角色发了 `room.apply` 权限；
- 「多级审批」实际只按 `currentLevel` 自增，两级使用同一个 `room.approve` 权限，**同一个账号可以连续点两次通过**；
- 审批人不校验是否等于申请人；
- 审批通过时不复查时段冲突，两个待审申请可以先后都通过；
- 「超时」只定义为「提交后 N 小时未审批」，未与活动开始时间关联。

## 2. 决策驱动因素

1. 规则必须能被一句话解释清楚，且在演示时可复现。
2. 审批的**独立性**（不同人、不同层级）是多级审批的意义所在，不能用同一权限糊弄过去。
3. 超时与冲突必须给出确定结果，不能「静默成功但什么都没做」。
4. 改动集中在 M2 目录内，尽量少触碰 M1/M3。

## 3. 状态机

### 3.1 状态

| 状态 | 含义 | 终态 |
|------|------|------|
| `PENDING` | 待审批，当前处在 `currentLevel` 级 | 否 |
| `APPROVED` | 全部层级通过，已写入占用（ADR-0002 的 space 级记录） | 否，可被撤销 |
| `REJECTED` | 任一层级驳回 | 是 |
| `CANCELLED` | 申请人主动撤销 | 是 |
| `EXPIRED` | 审批超时，系统自动撤销 | 是 |

不设置 `ACTIVE` / `COMPLETED`。理由：占用由时间区间表达（ADR-0002），到了时段自然失效，不需要定时任务去推进状态。少一个定时任务就少一类「任务没跑导致状态卡住」的故障。

### 3.2 迁移表

| 当前 | 触发 | 执行者 | 守卫条件 | 副作用 |
|------|------|--------|----------|--------|
| — | 提交 | 申请人 | 具 `room.apply`；时段合法；无冲突 | 创建 `PENDING`，`currentLevel=1`，计算 `timeoutAt` |
| `PENDING` | 通过 | 具 `room.approve.l{level}` 的审批人 | 非申请人；本级未审批过；再次冲突校验通过 | 写审批记录；`level < maxLevel` → 层级 +1 仍 `PENDING`；否则 → `APPROVED` + 写占用 |
| `PENDING` | 驳回 | 同上 | 非申请人；驳回意见必填 | 写审批记录；→ `REJECTED` |
| `PENDING` | 撤销 | 申请人本人 | — | → `CANCELLED` |
| `PENDING` | 超时 | 系统 | `now > timeoutAt` | → `EXPIRED`，通知申请人 |
| `APPROVED` | 撤销 | 申请人本人 | 活动开始时间之前 | → `CANCELLED`，释放占用 |

其余组合一律拒绝，并返回明确错误码（如 `INVALID_STATE_TRANSITION`），不允许静默成功。

## 4. 权限门槛

| 权限码 | 授予角色 | 说明 |
|--------|----------|------|
| `room.apply` | 教师、教工、院系管理员 | **学生个人不具备**（修正脚手架与需求的矛盾） |
| `room.approve.l1` | 教室管理员 / 院系管理员 | 一级：本院系教室与常规时段 |
| `room.approve.l2` | 教务处 | 二级：终审 |

多级审批的**独立性**由两条硬校验保证：

1. 审批人 ≠ 申请人；
2. 第二级审批人 ≠ 第一级审批人。

这两条不满足就拒绝，不允许「同一人两次点击完成多级审批」——那样多级审批只是形式。

## 5. 超时语义

```
timeoutAt = min(提交时刻 + ROOM_APPROVAL_TIMEOUT_HOURS,
                活动开始时刻 - ROOM_APPROVAL_CUTOFF_HOURS)
```

- 只对 `PENDING` 生效；已通过的单子不因审批超时而撤销。
- 第二个上界防止「审批时限还没到，活动已经开始了」这种无意义的待审单。
- 两个参数均可在 `system_configs` 中调整，默认 24 与 2。
- 定时任务用条件更新实现幂等：

```sql
UPDATE room_booking_requests
   SET status = 'EXPIRED', decidedAt = :now
 WHERE status = 'PENDING' AND timeoutAt < :now
```

影响行数即本次处理数量，重复执行不会二次处理。

## 6. 冲突策略（与 M1 个人预约的关系）

整教室申请与已有个人预约冲突时，**拒绝申请**，而不是驱逐已预约的学生。

理由：

- 个人预约是学生已经获得的确定预期，撤销会造成实际损失（人已经到教室）；
- 「后来者优先」会让掌握信息的人可以随时挤占，缺乏公平性；
- 拒绝 + 明确提示（「该时段已有 N 个座位被预约，建议改选时段」）是可解释、可复现的行为。

审批通过前**再校验一次**冲突，防止提交后到审批前这段时间里被个人预约插入。

## 7. 并发与幂等

- 状态迁移与占用写入在**同一事务**内完成。
- 通过/驳回使用条件更新：`UPDATE ... WHERE id = ? AND status = 'PENDING' AND currentLevel = ?`，影响行数为 0 表示已被处理，返回冲突错误而不是覆盖。
- 审批记录采用「每级最多一条」的约束（`requestId + level` 唯一），重复提交会撞唯一约束而不是写出两条记录。

## 8. 不在本次范围内

明确记为「未实现」，不从清单里消失（任务书要求）：

- 审批转交、加签、撤回；
- 周期性预约（每周三下午等）；
- 按教室容量/时长自动决定审批级数（v1 固定 2 级，参数化留到 v2）；
- 审批意见模板与常用理由。

## 9. 影响

- 实体：`RoomBookingRequest` 增加 `version` 或沿用 `updatedAt` 做乐观并发；状态枚举改为大写常量并集中定义。
- 权限：种子数据新增 `room.approve.l1` / `room.approve.l2`，从 `student` 角色移除 `room.apply`。
- 测试：`backend/test/m2-rooms.spec.ts` 需按状态机重写，覆盖非法迁移、自审批拦截、两级同人拦截、超时边界。
- 需求：`docs/requirements.md` 中 M2-01 的表述与 M2 各条状态需要同步修正。
