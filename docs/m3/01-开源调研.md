## 1. 调研目的

M3 模块（物业报修工单）在雏形中已有可运行骨架，需判断两件事：

1. 是否存在**可直接复用**的开源实现，能省掉主体开发量；
2. 若不能直接复用，有哪些**成熟设计模式**值得借鉴，避免自己拍脑袋设计状态机与 SLA。

## 2. 调研方法

- 通过 GitHub REST Search API 检索（`/search/repositories`），按 star 数排序；
- 关键词组合：`maintenance work order`、`cmms`、`repair management system`、`helpdesk ticket system`、`报修`、`nestjs ticket`；
- 对候选项目进一步读取目录结构、数据模型定义（如 Frappe DocType 的 JSON schema），而非只看 README；
- 筛选标准：① 有真实生产使用；② 领域为「设施/设备维修」或「工单流转」；③ 数据模型可读。

> 说明：本次检索受网络环境影响，`github.com` 主站间歇不可达，全部检索走 `api.github.com`，读取源码走 Contents API。以下 star 数取自 2026-10-27。

## 4. 重点项目的可借鉴点

### 4.1 frappe/helpdesk（参考价值最高）

读取 `HD Ticket` 与 `HD Service Level Agreement` 两个 DocType 的字段定义后，提取出以下设计：

| 设计点 | 其实现方式 | 我们雏形的差距 |
|---|---|---|
| **双时限 SLA** | `response_by`（首响时限）+ `resolution_by`（解决时限）两个独立字段 | 只有一个 `slaDeadline`，无法考核「多久接单」 |
| **SLA 计时可暂停** | `on_hold_since` + `total_hold_time`，挂起期间停止计时 | 完全没有，等待配件的时间会算进超时 |
| **SLA 状态机** | `agreement_status`：Fulfilled / Failed / Paused / First Response Due | 只有 escalateLevel 计数，无 SLA 结论 |
| **工时统计** | `first_response_time`、`avg_response_time`、`resolution_time`、`user_resolution_time` | 无 |
| **状态分组** | `status_category`（Open / Paused / Resolved / Closed），状态可配置但归入固定分类 | 状态硬编码 6 个，无分组，统计口径难统一 |
| **派单池** | `agent_group`（班组）+ `hd_team` / `hd_team_member` | 只有单个 `assigneeId`，无「派给哪个班组」 |
| **重复工单合并** | `is_merged` + `merged_with` | 无，同一房间重复报修会重复下架/恢复 |
| **验收不通过重开** | `ticket_reopen_status` | 无，验收只能通过 |
| **反馈选项** | `hd_ticket_feedback_option`（如「解决速度慢」） | 只有自由文本 + 1~5 分 |
| **SLA 按工作日历** | `holiday_list` + `hd_service_day` + `hd_holiday` | 纯自然时 48 小时，跨周末不合理 |
| **工单活动时间线** | `hd_ticket_activity` 独立表 | 无，只有 4 个时间戳字段 |

### 4.2 Grashjs/cmms（领域最贴近）

- `Request`（报修申请）与 `WorkOrder`（执行工单）**分离**：申请是「有人报了个问题」，工单是「安排人去做」。我们的雏形把两者合成一条记录，适合课程规模，不引入分离。
- 完整的资产维度：`Asset`、`Location`、`AssetDowntime`、`Part`、`Labor`、`PreventiveMaintenance`。
  - 我们只借鉴 **Location 维度**：工单必须明确挂在 `space`（房间）或 `seat`（座位）上，这是与 M1 座位联动的锚点。
  - 维修备件（Part）、工时成本（Labor）、预防性维护（PM）判定为**超出课程范围**，不采用。

### 4.3 osTicket / zammad（流程参考）

- **转派（Transfer）与改派**是标准能力：派错人是常态，系统必须支持在 `dispatched` 状态下换人，且要留痕。我们雏形只能「取消重报」，这是明显缺口。
- **超时升级（Overdue → Escalation）**：超时不是简单计数，而是升级到更高处理层级（组长/主管）并由其接管。我们雏形的 `escalateLevel + 1` 之后没有任何实际动作，属于「假升级」。

## 5. 结论

### 5.1 不直接复用开源代码

理由：

1. **技术栈不匹配**：无 NestJS + TypeORM 实现，引入 PHP/Ruby/Java 系统等于换栈重写；
2. **体量不匹配**：zammad / osTicket 均为数十万行级产品，课程项目无法在周期内消化；
3. **核心耦合无法迁移**：M3 的价值在于「维修中自动下架该室座位、验收后恢复」，这依赖本校项目的 `SeatStateService` 与 `SeatStatusLog`，任何外部系统都不具备；
4. **评分导向**：课程考核看的是自研过程（需求→设计→实现→测试），直接套壳反而失分。

### 5.2 采用「借鉴模式、自研实现」

确定借鉴以下 8 项（已在 ADR-0002 固化）：

1. 双时限 SLA（首响 + 解决），替代单一 `slaDeadline`；
2. SLA 挂起暂停计时（`onHold`）；
3. SLA 结论状态（达标 / 超时 / 进行中）；
4. 工单事件时间线独立表（可追溯，替代散落的时间戳字段）；
5. 状态分类（未完结 / 挂起 / 待验收 / 已关闭）统一统计口径；
6. 改派（reassign）作为标准能力，留痕不改工单号；
7. 重复工单合并（merged），避免重复下架；
8. 验收不通过 → 返工重开（reopen），而非新建工单。

明确**不采用**：备件库存、工时成本核算、预防性维护排程、多租户、邮件工单入口、客服知识库。
