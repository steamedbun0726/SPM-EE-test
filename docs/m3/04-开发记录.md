## 2026-10-20 ｜ S0 环境准备

### 1. 仓库获取（遇到两个障碍）

- **障碍一：私有仓库匿名不可见。** 直接 `git clone https://github.com/steamedbun0726/SPM-EE-test` 返回 `remote: Repository not found`。查证方式：
  - `GET /repos/steamedbun0726/SPM-EE-test` → `404`
  - `GET /users/steamedbun0726` → `200`，且 `public_repos = 0`
  - 结论：仓库存在但为 **Private**，匿名访问永远 404。**接受协作者邀请只让浏览器可见，命令行仍需凭据**——这一点最初被误解，记录在此避免组内重复踩坑。
- **障碍二：网络对 github.com 主站不稳定。** 期间多次出现 `CONNECT tunnel failed, response 502`，`curl https://github.com` 返回 `000`；但 `api.github.com`、`codeload.github.com`、`objects.githubusercontent.com` 稳定可用。
- **处置**：先用 `GET /repos/...` 确认仓库元信息（`private: true`，描述「软件过程管理和工程伦理课程项目」），再重试 clone，第二次成功。

> 安全约定：拉取使用临时 Personal Access Token，**克隆完成后立即** `git remote set-url` 还原为不含凭据的地址，`.git/config` 中不留明文；Token 用后由本人在 GitHub 侧撤销。文档与日志中不记录 Token 值。

- **证据**：`git log` 显示 `08e5cb2`（HEAD）与 `3359756`（雏形），`git status` 干净，`origin` 为无凭据 URL。

### 2. 一次操作失误与恢复

- 将临时克隆目录并入工作区时，根目录的 `README.md`、`AGENTS.md`、`.gitignore`、`docker-compose.yml` 未被正确搬移，`git status` 显示 4 个文件为 `D`（deleted）。
- **处置**：确认这些文件在 HEAD 中存在后，`git restore .` 一次性恢复，未使用任何手工拷贝。
- **教训**：跨目录搬运用 `git restore` 兜底比手工补文件可靠；任何「文件消失」先判断是否在版本库中。

### 5. 端到端接口验证（真实 HTTP，非 mock）

启动 `npm run start`，`GET /api/health` → `{"status":"ok"}`。随后用种子账号走完整链路：

| 步骤 | 接口 | 结果 |
|---|---|---|
| 学生登录 | `POST /api/auth/login` | 拿到 JWT |
| 上报前座位 | `GET /api/spaces/1/seats` | 10 个座位，全部 `available` |
| 上报报修 | `POST /api/m3/work-orders`（spaceId=1） | `WO-20261020-001`，`reported` |
| 上报后座位 | `GET /api/spaces/1/seats` | 10 个座位 `maintenance`，来源 `M3` |
| 派单 | `POST /:id/dispatch`（admin → 维修员 id=4） | `dispatched` |
| 开工 / 完工 | `POST /:id/start`、`POST /:id/complete` | `in_progress` → `completed` |
| 验收 | `POST /:id/accept`（rating=5） | `accepted` |
| 验收后座位 | `GET /api/spaces/1/seats` | 恢复 `available`，来源 `M3` |

- **结论**：M3-01 ~ M3-06 与跨模块写回 I-01 在真实运行环境下成立，不只是测试通过。
- **顺带发现**：`GET /api/users` 实际返回 404（`UsersController` 疑似未注册路由），权限信息可从 `/api/auth/me` 获取。与本模块无关，记录备查。

## 2026-10-27 ｜ S1 调研与设计

### 1. 开源调研（详见 `docs/m3/01-开源调研.md`）

- 方法：GitHub Search API 检索 + Contents API 读真实数据模型，不看 README 下结论。
- 候选：zammad（6038★）、osTicket（3994★）、frappe/helpdesk（3450★，Vue）、Peppermint（3161★）、Grashjs/cmms（845★）。
- **结论 1**：不存在 NestJS + TypeORM + Vue3 的同栈工单系统，无「拿来即用」选项。
- **结论 2**：采用「借鉴模式、自研实现」，采纳 8 项设计（双时限 SLA、挂起暂停、SLA 结论、事件时间线、状态分类、改派、合并、返工）。
- **结论 3**：明确排除备件库存、工时成本、预防性维护、多租户等超范围能力。

### 2. 代码盘点（形成缺口清单）

| 缺口 | 证据 |
|---|---|
| 单座位报修不下架 | `work-orders.service.ts:105` 仅在 `targetType==='space'` 时调 `setMaintenance` |
| 无事件留痕 | 实体只有 `dispatchedAt / inProgressAt / completedAt / acceptedAt` 四个时间戳 |
| 不能改派 | `dispatch()` 要求状态为 `reported`，`dispatched` 后再派返回 409 |
| 验收单向 | `accept()` 只写 `accepted`，无失败分支 |
| 升级无处置 | `escalateOverdue()` 仅 `escalateLevel += 1` + 通知上报人 |
| 权限不全 | 种子仅有 `workorder.report` / `workorder.dispatch`；`start/complete` 无 `@Permissions` |
| SLA 单一 | 只有 `slaDeadline`，无首响时限、无挂起暂停 |
