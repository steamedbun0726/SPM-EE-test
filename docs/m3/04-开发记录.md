## 2026-10-20 ｜ S0 环境准备

### 1. 仓库获取（遇到两个障碍）

- **障碍一：私有仓库匿名不可见。** 直接 `git clone https://github.com/steamedbun0726/SPM-EE-test` 返回 `remote: Repository not found`。查证方式：
  - `GET /repos/steamedbun0726/SPM-EE-test` → `404`
  - `GET /users/steamedbun0726` → `200`，且 `public_repos = 0`
  - 结论：仓库存在但为 **Private**，匿名访问永远 404。**接受协作者邀请只让浏览器可见，命令行仍需凭据**——这一点最初被误解，记录在此避免组内重复踩坑。
- **障碍二：网络对 github.com 主站不稳定。** 期间多次出现 `CONNECT tunnel failed, response 502`，`curl https://github.com` 返回 `000`；但 `api.github.com`、`codeload.github.com`、`objects.githubusercontent.com` 稳定可用。
- **处置**：先用 `GET /repos/...` 确认仓库元信息（`private: true`，描述「软件过程管理和工程伦理课程项目」），再重试 clone，第二次成功。

> 安全约定：拉取使用临时 Personal Access Token，**克隆完成后立即** `git remote set-url` 还原为不含凭据的地址，`.git/config` 中不留明文；Token 用后由本人在 GitHub 侧撤销。文档与日志中不记录 Token 值。

- **证据**：`git log` 显示 `08e5cb2`（HEAD）与 `3359756`（雏形），`git status` 干净，`origin` 为无凭据 URL。

### 2. 一次操作失误与恢复

- 将临时克隆目录并入工作区时，根目录的 `README.md`、`AGENTS.md`、`.gitignore`、`docker-compose.yml` 未被正确搬移，`git status` 显示 4 个文件为 `D`（deleted）。
- **处置**：确认这些文件在 HEAD 中存在后，`git restore .` 一次性恢复，未使用任何手工拷贝。
- **教训**：跨目录搬运用 `git restore` 兜底比手工补文件可靠；任何「文件消失」先判断是否在版本库中。

## 2026-10-27 ｜ S1 调研与设计

### 1. 开源调研（详见 `docs/m3/01-开源调研.md`）

- 方法：GitHub Search API 检索 + Contents API 读真实数据模型，不看 README 下结论。
- 候选：zammad（6038★）、osTicket（3994★）、frappe/helpdesk（3450★，Vue）、Peppermint（3161★）、Grashjs/cmms（845★）。
- **结论 1**：不存在 NestJS + TypeORM + Vue3 的同栈工单系统，无「拿来即用」选项。
- **结论 2**：采用「借鉴模式、自研实现」，采纳 8 项设计（双时限 SLA、挂起暂停、SLA 结论、事件时间线、状态分类、改派、合并、返工）。

### 顺带修复：种子数据增量失效

原 `SeedService` 的幂等策略是「权限表为空才整批插入」「角色已存在则跳过」。后果是**在已有开发库上新增权限码不会生效**——本次新增的 4 个权限码与角色绑定就属于这种情况。改为按 `code` 逐条补齐权限、角色已存在时补权限差集，保持幂等且能增量生效。

### 发现并修复的 2 处缺陷（均属 D1 公共层，非 M3 模块内）

**缺陷 1：`/api/users`、`/api/roles` 全部 404**

- 现象：管理员打开「用户管理」「角色与权限」直接报错，页面空白。
- 根因：`shared/rbac/rbac.controller.ts` 中定义了 `UsersController` 与 `RolesController`，但**没有任何模块把它们放进 `controllers`**。Nest 只装配被模块声明的控制器，孤立的 `@Controller()` 装饰器不会自动生效。
- 修复：新建 `shared/rbac/rbac.module.ts` 注册两个控制器与 `UsersService`/`RolesService`，由 `SharedModule` 引入并转出。
- 首次修复尝试踩坑：在 `SharedModule` 的 `exports` 里直接写 `UsersService` 会让应用启动失败 —— Nest 要求被导出的 token 必须位于本模块的 `providers` 或 `imports` 中，正确写法是转出整个 `RbacModule`。

**缺陷 2：用户接口把 `passwordHash` 返回给客户端**

- 现象：`GET /api/users` 的响应里每个用户都带 `"passwordHash": "$2a$10$..."`。
- 影响：任何能打开用户管理页的人都能从浏览器网络面板拿到全部账号的 bcrypt 哈希，可离线爆破。属信息泄漏。
- 根因：`UsersService.decorate()` 用 `{ ...user, roleCodes, permissionCodes }` 直接展开实体。
- 修复：新增 `PublicUser = Omit<UserWithRoles,'passwordHash'>` 与 `toPublic()`，`findById` / `findAll` / `findByPermission` / `create` / `update` 全部收敛到该类型；`findByUsername` 刻意保留哈希（`verifyPassword` 需要），并在注释中标明「仅供认证流程」。

**附带修正**：`findAll` 只 join 了 `u.roles`，没有 join `roles.permissions`，导致返回的 `permissionCodes` 恒为 `[]`。前端若据此判断会得到「该用户没有任何权限」的错误结论。已补 join —— 这一条是**测试写出来才发现的**，不是靠看代码看出来的。

## S4 跨模块合并可行性验证（2026-10-28）

4. `npx tsc --noEmit` + `npx jest`；
5. `git reset --hard 1f5e6b7` 还原到 M3 分支状态。

### 结果

| 检查项 | 结果 |
|---|---|
| 文件重叠 | 2 个：`backend/src/modules/m1-seats/reservations.service.ts`、`docs/requirements.md` |
| 文本冲突 | **0**，`merge-tree` 与真实合并均为 clean |

## S6 三期收尾：挂起 / 合并 / 维修记录 / 统计看板（2026-10-28）

**背景**：`02-需求规格.md` 里 M3-14 / M3-15 / M3-17 / M3-18 一直停在「已定义、未实现」，是 v1.0 需求表上最后的四个空洞。四项都涉及口径取舍（挂起怎么停表、合并算不算工单量、达标率拿哪个时限算），先写 ADR-0006 定策略，再落实现。

### 数据模型

新增迁移 `1780000003000-m3-hold-merge-stats`，13 个 `ADD COLUMN` + 2 个索引，全 `ADD COLUMN`、双库兼容、`down` 逐列 `try/catch`：

| 分组 | 字段 | 用途 |
|---|---|---|
| 挂起 | `holdReason` / `holdRequested` / `holdRequestedAt` / `holdRequestedBy` / `onHoldSince` / `preHoldStatus` / `totalHoldMinutes` / `holdEscalated` | 两级确认 + SLA 暂停 |
| 合并 | `mergedIntoId` / `mergedCount` | 合并关系与主线吸收数 |
| 维修记录 | `resolutionNote` | 完工必填说明 |
| 统计口径 | `firstRespondedAt` / `originalSlaDeadline` | 首响终点、不受升级推后的原始时限 |

其中 `originalSlaDeadline` 是本轮最关键的一个字段。既有 `escalateOverdue` 每次升级都会把 `slaDeadline` 往后推 `WORKORDER_ESCALATE_HOURS`，**如果拿它算 SLA 达标率，所有被升级过的工单都显示「未超时」，指标必然虚高**。所以另存一份只随挂起平移、永不参与催促的原始值。

### 实现要点

1. **挂起（M3-14）**：`requestHold → confirmHold → resumeFromHold` 三级动作。申请阶段**状态与时限都不动**（测试有显式断言），派单员确认后才置 `on_hold`。理由写在 ADR-0006 决策 1：挂起等于暂停考核，允许自行停表则 SLA 制度失效。恢复时三个时限字段同时平移，不重算。
2. **合并（M3-15）**：判重 409 响应体补 `existingWorkOrderId` / `existingWorkOrderNo` / `existingWorkOrderStatus`，前端据此提供「合并到该工单」。合并单落 `merged`、无独立时限、**不产生任何座位下架**；事后合并时被合并单清空自身 `seatIds`，把恢复责任整体交给主线。
3. **维修记录（M3-17）**：`complete` 强制 `resolutionNote`，空则 400；完工可补传照片，与上报照片合并去重后仍受 3 张上限约束。**这是破坏性变更，前后端必须同时上线**。
4. **统计看板（M3-18）**：`GET /stats` 返回 KPI + 分组 + 空间排行，并把每个指标的分母口径以 `definitions` 字段随数据返回。三条口径：完工率分母剔除取消/合并单、解决时长扣挂起、SLA 达标率用原始时限。
5. **跨模块**：D 层 `StatsView.vue` 增加 M3 区块（6 KPI + 分类分布 + 空间排行 + 可展开口径说明），符合需求「需在 D 层增加 M3 区块」的要求。

### 测试当场抓到的一处缺陷

`mergeInto`（事后合并）漏写 `wo.mergedIntoId = main.id` —— 状态改成了 `merged`、座位清单也交出去了，但合并指向是空的。这种缺陷肉眼 review 很容易放过（时间线里 `merged` 事件、主线 `merge_absorbed` 事件都正常），只有断言「对被合并单反查主线」才会暴露。

### 界面验证时发现的既有缺陷：首响超时每轮重复升级

派单台截图里，10-27 的几张工单 `升级层级` 显示为 **113**。追查原因：`escalateOverdue` 的查询条件包含 `{ status: 'reported', responseDeadline < now }`，但升级时只把 `slaDeadline` 推后 `WORKORDER_ESCALATE_HOURS`，**没有推后 `responseDeadline`**。于是同一张单每跑一轮调度就重新命中，`escalateLevel` 无限累加，并每轮重发一次通知。

- **影响**：升级层级失去意义（113 级与 1 级在界面上无法区分严重程度）；通知轰炸报修人与派单员；`escalated` 标记永远为真，升级队列被长期占位。
- **修复**：升级时若 `responseDeadline` 已过期，同步推后到 `now + escalateHours`，与本轮 SLA 窗口对齐。
- **未回溯历史数据**：已累加的 113 级是脏数据，但属于本地开发库；生产环境如已上线需单独刷数（`escalateLevel` 按实际升级轮次重算或统一归零后依赖新窗口重新累积）。
- 这个缺陷与本轮「挂起超期只告警一次」属同类问题（定时任务缺少幂等保护），因此挂起超期扫描一开始就带了 `holdEscalated` 标记。

### 遗留与风险

1. **前后端耦合**：维修说明必填是接口契约变更，后端先上线会让旧前端的完工请求全部 400。部署时必须同版本发布。
2. **合并单未覆盖座位**：若合并单涉及主线未覆盖的座位（理论上不会，真重复必然座位有交集），按验收标准「座位状态不变」不下架，改为通知派单员人工处置。这是有意留的一手，已在 ADR-0006 记录。
3. **挂起超期只告警不自动恢复**：升级后仍需人工恢复或改派，避免系统擅自把停摆的单推回流程制造虚假进展。
4. `GET /stats` 按 `createdAt` 落入区间统计，跨区间长尾工单（上月上报、本月完工）不会计入本月分母，这是「按上报量考核」的口径选择，若需「按完工量考核」需另加参数。


## S7 补齐 M3-16：列表筛选、分页与搜索（2026-10-28）

三期交付后核对 `docs/requirements.md` 时发现，M3-16 一直标的是 🔴 且从未实现：`GET /mine` 只有 `status` 一个参数，`GET /pending`、`GET /assignments` 既无筛选也不分页，关键字搜索完全缺失。这是 18 条 M3 需求里唯一没有落地的条目，补齐。

### 接口设计

`GET /m3/work-orders`（权限 `workorder.dispatch` / `workorder.manage` / `workorder.stats` 任一，权限守卫是「任一匹配」语义），返回 `{ items, total, page, pageSize }`。

筛选维度：`status`（支持 `reported,dispatched` 逗号多值）、`category`、`priority`、`spaceId`、`assigneeId`、`reporterId`、`escalated`、`from`/`to`、`keyword`；排序 `createdDesc`（默认）/`createdAsc`/`slaAsc`/`priority`。

**不动既有三个队列接口**。`/mine`、`/pending`、`/assignments` 的语义是固定的工作队列（各自的排序与过滤本身就带着业务含义，比如待派单按优先级 CASE 排），台账是叠加的全量检索入口。把队列接口改造成「带一堆可选参数」会让「派单台为什么少了单」这类问题变得难查。

### 四处刻意选择

1. **时间区间用闭区间**，与统计接口刻意不同。统计算的是「区间内的完成量」，右开是为了不重复计入边界；台账回答的是「10-28 那天有哪些单」，同一天到同一天必须有结果。两处口径不一致是自觉的，不是疏漏。
2. **转义 LIKE 通配符**并显式 `ESCAPE`。不转义时 `%` 会退化成「匹配任意串」，把「查无此单」变成「返回全部」——查问题的人会把这个结果当成事实。
3. **越界页码返回空列表而不是 500**，非正/非整数页码按第 1 页处理，`pageSize` 上限 100。台账是运营每天翻的页面，一次 500 就是整页白屏。
4. **无时限工单在 `slaAsc` 下排最后**。已合并单 `slaDeadline` 为空，SQLite/PG 的 ASC 都把 NULL 排在最前，不显式处理的话它们会永远占据第一页。
