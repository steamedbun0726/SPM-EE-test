## 1. 范围

本文档定义 M3 模块在雏形基线之上的**增量需求**。基线需求（M3-01 ~ M3-06）已实现并通过测试，不再重复描述，仅在追踪矩阵中引用。

不做的事情（明确排除）：备件库存管理、维修工时成本核算、预防性维护排程、邮件/微信工单入口、多租户隔离、客服知识库。理由见调研报告第 5.2 节。

## 2. 术语

| 术语 | 定义 |
|---|---|
| 工单 | 一次报修从上报到关闭的完整记录，编号 `WO-YYYYMMDD-NNN` |
| 报修对象 | `space`（整个房间）/ `seat`（单个座位）/ `other`（其他设施，如空调、门锁） |
| 下架 | 座位状态置为 `maintenance`，不再出现在 M1 可预约列表中 |
| 首响 | 维修员首次接单（`dispatched → in_progress`）的时刻 |
| 返工 | 验收不通过后，工单退回维修中状态重新处理 |
| 挂起 | 因等配件、等外部单位等客观原因暂停处理，期间 SLA 停止计时 |
| SLA 达标 | 首响与解决均在约定时限内完成 |

## 3. 角色与权限

| 角色 | 系统角色码 | 职责 | 需要的权限码 |
|---|---|---|---|
| 报修人 | `student` / `teacher` | 上报故障、查看自己工单、验收、评价 | `workorder.report`、`workorder.accept` |
| 维修员 | `maintenance` | 接单、维修、完工、申请挂起 | `workorder.handle` |
| 派单员 | `ops` / `admin` | 派单、改派、合并、升级处置、查看统计 | `workorder.dispatch`、`workorder.manage`、`workorder.stats` |
| 系统 | — | SLA 计时、超时升级、自动恢复座位 | 无（定时任务） |

现状缺口：权限码只有 `workorder.report` 与 `workorder.dispatch` 两个，`start` / `complete` 接口仅靠 `assigneeId` 比对，不具备权限模型意义上的控制。

## 4. 功能需求

优先级：**P0 = 本期必做**（跨模块集成与正确性），**P1 = 本期应做**（流程完整性），**P2 = 有余力再做**（统计与体验）。

### P0

#### M3-07 单座位粒度报修与下架

- **描述**：当报修对象为某个座位（`targetType='seat'`）时，只有该座位下架，房间内其他座位保持可预约；验收通过或取消后仅恢复该座位。
- **现状**：`targetType='seat'` 时 `targetId` 只被存下来，没有任何座位状态联动，坏椅子仍可被预约。
- **验收标准**：
  1. 给定房间 R 有 3 个座位，对座位 S2 上报工单，则 S2 状态为 `maintenance`、来源 `M3`，S1/S3 仍为 `available`；
  2. 该工单验收通过后，S2 恢复 `available`，且 `SeatStatusLog` 中存在 `from=maintenance → to=available` 且 `refType='work_order'` 的记录；
  3. 座位已被其它未完结工单下架时，重复上报返回 `409`，不重复写日志。
- **涉及**：`SeatStateService` 新增座位粒度方法；`WorkOrdersService.report / accept / cancel`。

#### M3-08 工单事件时间线

- **描述**：每一次状态流转、改派、挂起、返工、合并都写入工单事件表，形成可查询的时间线。
- **现状**：只有 `dispatchedAt / inProgressAt / completedAt / acceptedAt` 四个时间戳，改派、挂起、返工等动作无记录，审计日志只到 HTTP 层。
- **验收标准**：
  1. 一张工单走完「上报→派单→开工→完工→验收」，事件表恰好 5 条，按时间升序返回；
  2. 每条事件包含：类型、原状态、新状态、操作人、备注、时间；
  3. 详情接口 `GET /m3/work-orders/:id/events` 返回该工单全部事件，非本人工单返回 `403`。
- **涉及**：新增实体 `WorkOrderEvent` + 迁移；Service 内统一写入。

#### M3-09 改派

- **描述**：派单员可在 `dispatched` 或 `in_progress` 状态下把工单改派给另一名维修员，工单号不变。
- **现状**：派错人只能取消重报，导致 `WO-` 编号浪费且座位被重复下架/恢复。
- **验收标准**：
  1. `dispatched` 状态改派后 `assigneeId` 更新为新维修员，状态不变，时间线新增一条「改派」事件（含原维修员）；
  2. 原维修员调用 `start / complete` 返回 `403`；
  3. `completed / accepted / cancelled` 状态改派返回 `409`。
- **涉及**：`dispatch` 支持 `reassign` 语义或新增 `reassign` 接口；权限 `workorder.dispatch`。

#### M3-10 验收不通过与返工

- **描述**：报修人验收时可选择「通过」或「不通过」。不通过须填原因，工单退回 `in_progress`，维修员需重新处理。
- **现状**：验收只能通过，`completed` 是单向终点。
- **验收标准**：
  1. 验收不通过后工单状态回到 `in_progress`，`completedAt` 清空、`reopenCount + 1`，时间线记录原因；
  2. 座位**保持下架**（不因返工而恢复）；
  3. 返工后再完工、再验收通过，座位恢复；
  4. 同一工单返工超过 3 次（可配置 `WORKORDER_MAX_REOPEN`），后续验收只能通过或升级处理，防止无限循环。
- **涉及**：`accept` 增加 `result` 参数；新增 `reopenCount` 字段。

#### M3-11 权限码补全与越权防护

- **描述**：为维修相关接口补齐权限码，同时保留「本人」校验。
- **验收标准**：
  1. `start / complete / hold` 需要 `workorder.handle` 权限且为当前指派人；
  2. `dispatch / reassign / merge` 需要 `workorder.dispatch`；
  3. 无权限调用返回 `403`，且不产生任何数据变更（含事件、日志）。
- **涉及**：`work-orders.controller.ts` 补 `@Permissions`；种子数据补权限码与角色绑定。

#### M3-12 超时升级的实质处置

- **描述**：SLA 超时后不能只把 `escalateLevel + 1` 了事，须产生可被处理的后果。
- **现状**：`escalateOverdue` 只累加计数并通知报修人，派单员不感知，工单不会改变流向。
- **验收标准**：
  1. 超时后工单被标记 `escalated=true`，并出现在派单员的「升级待处理」列表中；
  2. 通知同时发给报修人与派单员（`workorder.dispatch` 权限持有者）；
  3. 升级后再超时（每 `WORKORDER_ESCALATE_HOURS`）累加层级，但同一层不重复通知；
  4. 升级后若被改派或完工，标记清除。
- **涉及**：`escalateOverdue`、新增查询接口、通知逻辑。

### P1

#### M3-13 双时限 SLA（首响 + 解决）

- **描述**：上报时同时计算首响时限 `responseDeadline = now + WORKORDER_RESPONSE_HOURS`（默认 4h）与解决时限 `resolveDeadline = now + WORKORDER_SLA_HOURS`（默认 48h）；维修员接单时记录 `firstRespondedAt`。
- **验收标准**：
  1. 上报后两个时限字段均非空且满足配置小时数；
  2. 首响早于 `responseDeadline` 则 SLA 首响达标，晚于则为超时，可在详情中看到结论；
  3. 修改 `WORKORDER_RESPONSE_HOURS` 配置后新工单按新值计算，历史工单不变。
- **说明**：保留旧字段 `slaDeadline` 作为解决时限的兼容别名，避免破坏既有测试与前端。

#### M3-14 挂起与恢复（SLA 暂停计时）

- **描述**：维修员可申请挂起（须填原因，如「等厂家配件」），派单员确认后生效；挂起期间 SLA 停止计时，恢复后继续。
- **验收标准**：
  1. 挂起后状态为 `on_hold`，`onHoldSince` 有值，解决时限按挂起时长顺延；
  2. 挂起状态下定时任务不判定其超时；
  3. 恢复后状态回到挂起前的状态（`dispatched` 或 `in_progress`），`totalHoldMinutes` 累加；
  4. 挂起时长超过 `WORKORDER_HOLD_MAX_DAYS`（默认 7 天）仍不恢复，自动升级并通知派单员；
  5. 挂起期间座位**保持下架**。
- **涉及**：新增状态 `on_hold`、字段 `onHoldSince / totalHoldMinutes / preHoldStatus`。

#### M3-15 重复工单合并

- **描述**：同一空间（或同一座位）已存在未完结工单时，新上报可选择「合并到已有工单」，合并后新工单标记 `merged` 并指向主线工单，不产生新的座位下架。
- **验收标准**：
  1. 上报时若检出同目标未完结工单，返回 `409` 并附已有工单号（前端提示可合并）；
  2. 携带 `mergeIntoId` 重新提交时，新工单状态为 `merged`、`mergedIntoId` 指向主线，座位状态不变；
  3. 主线工单验收后，座位正常恢复（而不是被合并单再次触发恢复）。
- **说明**：不做自动合并，避免误判；由报修人/派单员决定。

#### M3-16 列表筛选、分页与搜索

- **描述**：工单列表支持按状态、分类、优先级、空间、时间范围、关键字（编号/标题）筛选，并分页。
- **验收标准**：
  1. 各筛选项单独与组合使用结果正确（返回条数与直接查库一致）；
  2. 分页参数 `page/pageSize`，返回 `{ items, total, page, pageSize }`；
  3. 非法页码返回空列表而非 500。

#### M3-17 维修记录与现场照片

- **描述**：维修员完工时须填写维修说明（`resolutionNote`），可选上传照片（最多 3 张，存 URL 或 base64 长度受限），报修人验收时可见。
- **验收标准**：
  1. 完工不填维修说明返回 `400`；
  2. 照片数量超过 3 张返回 `400`；
  3. 验收页面可查看维修说明与照片。

### P2

#### M3-18 工单统计看板

- **描述**：统计工单量、完工率、平均首响时长、平均解决时长、SLA 达标率、返工率、各空间故障排行。
- **验收标准**：统计口径需在文档中写明（如「平均解决时长」是否含挂起时间），且与手工查询结果一致；跨模块影响：需在 D 层 `StatsView` 增加 M3 区块。

# 附录 A：v1.1 增量需求（M3-19 ~ M3-31）

| 项目 | 内容 |
|---|---|
| 版本 | v1.1（在 v1.0 的 M3-07~M3-18 之后追加） |
| 日期 | 2026-10-27 |
| 触发原因 | 一期实现复盘时识别出的 13 项缺口，其中 M3-24 被判定为**最严重漏洞** |
| 状态 | 全部已实现，验收标准与测试用例一一对应 |

## A.1 增量需求的由来

一期交付了状态机、时间线、改派、返工、权限与升级，但复盘时发现两个层面的问题：

1. **动作不完整**：有了「派单」，却没有「改了派怎么通知」「修不完怎么解释」「有争议怎么办」。
2. **副作用未处理**：下架只改了座位状态，**没有处理已经存在的预约**——学生约好的座位被维修，到点来了发现不能用，责任在系统。这是本批最严重的漏洞。

## A.2 功能需求

### P0

#### M3-19 部分 / 单座位下架

- **描述**：一间教室往往只有部分座位损坏。上报时可指定 `seatIds` 只下架受影响的座位，其余座位保持可预约；恢复时按清单精确回滚。
- **验收标准**：
  1. 房间 3 个座位，指定 2 个上报 → 这 2 个 `maintenance`，第 3 个仍 `available`；
  2. 验收通过后仅这 2 个恢复 `available`；
  3. 跨空间混选、座位不存在、座位已停用均返回 4xx 且不落任何状态变更。
- **实现**：`report` 的 `seatIds` 入参 + `wo.seatIds` 快照 + `SeatStateService.setSeatsMaintenance / restoreSeatsAfterMaintenance`。

#### M3-24 下架时处置已有预约（本批最高优先级）

- **描述**：座位下架后，立即作废该座位上尚未开始的预约并通知本人，**不计违约**；已开场/已签到的预约不取消，转人工协调。
- **验收标准**：
  1. 座位 S 有明日 10:00-12:00 的 `booked` 预约，对 S 上报工单后该预约变 `cancelled`；
  2. `violations` 表不新增记录（非用户原因，不得记违约）；
  3. 预约人收到「预约已被取消（座位维修）」通知；
  4. 工单时间线出现 `seats_released` 事件，note 含「作废预约 N 条」；
  5. 若预约时段已开始，预约**不改状态**，用户收到「座位维修提醒」，同时通知管理员「维修与在座用户冲突」需现场协调。
- **实现**：`ReservationsService.cancelForSeatsUnderMaintenance`（M1 公开方法）+ `WorkOrdersService.releaseAffectedReservations`。

### P1

#### M3-20 工单留言

- **描述**：上报人、维修员、派单员可在工单下留言，作为时间线事件留痕并通知对方。
- **验收标准**：留言写入 `workorder_events`（`type='commented'`）并携带操作人姓名快照；非参与人返回 `403`；空内容返回 `400`；接收方收到站内通知。

#### M3-21 预计恢复时间（ETA）

- **描述**：报修人最关心的往往不是「修没修完」而是「还要多久」。ETA 可由上报人填写、维修员更新，变更即通知。
- **验收标准**：ETA 必须晚于当前时间且在 `WORKORDER_ETA_MAX_DAYS`（默认 30）天内，否则 `400`；更新写入 `eta_updated` 事件并通知上报人；工单终态不可再改。

#### M3-22 维修员申诉与裁决

- **描述**：验收不通过时维修员可能不认同。允许其申诉，由派单员/管理员终裁，避免「拒验—返工」单方面循环。
- **验收标准**：
  1. 仅 `in_progress` 且 `reopenCount > 0` 的工单可申诉，否则 `409`；
  2. 已有待裁决申诉时重复申诉 `409`；同一工单申诉次数上限 `WORKORDER_MAX_APPEAL`（默认 2）；
  3. 裁决 `upheld`：维持返工，状态仍 `in_progress`，`reopenCount` 不变；
  4. 裁决 `overturned`：视同验收通过（`accepted`），`reopenCount - 1`，座位恢复，并通知双方；
  5. 裁决不可重复提交。
- **设计取舍**：`overturned` 直接终局关闭而不是退回 `completed` 让报修人再验一次，是为了避免无限循环；争议一旦进入管理员裁决，以裁决为终局。

#### M3-23 SLA 即将超时预警

- **描述**：剩余时限低于总时长 `WORKORDER_SLA_WARN_RATIO`（默认 20%）时提醒维修员与派单员。
- **验收标准**：同一时限窗口只提醒一次（`slaWarned`）；已超时的工单不在预警范围（交给升级任务）；升级任务重置 `slaWarned`，新窗口重新计算。
- **补充**：首响时限（`responseDeadline`）超时也会触发升级，事件 note 区分「首响超时」与「解决超时」。

### P2

#### M3-25 重复故障识别

- **描述**：同空间同分类故障在 `WORKORDER_DEGRADE_WINDOW_DAYS`（默认 30 天）内达到 `WORKORDER_DEGRADE_THRESHOLD`（默认 3 次）→ 标记 `degradedSuspected`，提示整体检修而非反复小修。
- **验收标准**：第 3 次同空间同分类上报后 `degradedSuspected=true`，前两次为 `false`；`GET /degraded` 可查。

#### M3-26 维修员负载与技能画像

- **描述**：派单员需要知道谁手上还有活、谁擅长这类故障，否则只能凭印象派单。
- **验收标准**：`GET /technicians` 返回每个具 `workorder.handle` 权限的在职用户：在手工单数、紧急数、历史完成数、平均评分、平均修复时长、Top3 高频分类。

#### M3-27 低分自动回访

- **描述**：验收评分 ≤ `WORKORDER_REVISIT_RATING`（默认 2）自动进入回访队列，不能只存分数没人跟。
- **验收标准**：低分后 `revisitRequired=true` 且进入 `GET /revisits`；`POST /:id/revisit` 记录处置说明后移出队列；重复处理 `409`；高分不触发。

#### M3-28 照片约束与访问控制

- **描述**：现场照片最多 `WORKORDER_MAX_PHOTOS`（默认 3）张，且地址协议白名单（`http(s)` / `/uploads/` / `/api/files/`），防 `javascript:` 注入。
- **验收标准**：超量 `400`；非法协议 `400`；补传走同一套校验；照片仅在有权查看工单的接口中返回。

#### M3-29 优先级真正生效

- **描述**：优先级若只体现在字段上、不影响时限和排队顺序，就只是个装饰字段。
- **验收标准**：
  1. SLA = 分类基线 × 优先级系数（urgent 0.3 / high 0.6 / medium 1 / low 1.5），同分类下 urgent 与 low 的时限相差 5 倍；
  2. 待派单队列按优先级降序排列，同级按解决时限升序。
- **设计取舍**：不给每个优先级配绝对小时数，而是锚定分类基线再缩放——因为「紧急的水电」和「紧急的桌椅」本就不该是同一时限。

#### M3-30 恶意误报限制

- **描述**：限制重复上报与高频取消，减少无效派工。
- **验收标准**：
  1. 同空间（座位有交集）已有未结工单时上报返回 `409`，提示已有工单号；
  2. 窗口期（默认 7 天）内自行取消达 `WORKORDER_MAX_CANCEL_PER_WINDOW`（默认 5）次后，上报返回 `409`，其他用户不受影响。
- **边界**：同房间不同座位的报修不算重复；只统计「自己取消」，不涉及被驳回场景，误伤面小。

#### M3-31 分类字典与前端选择器

- **描述**：分类从自由文本改为固定字典（8 类），前后端共用同一数据源。
- **验收标准**：`GET /m3/work-orders/meta` 返回分类（含标准时限）、优先级（含系数）、状态、各项限制；非法分类/优先级上报返回 `400`；前端选择器直接消费该接口，界面显示中文、提交字典码。

| ID | 需求 | 验收方式 |
