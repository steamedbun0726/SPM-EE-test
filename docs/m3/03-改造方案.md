## 1. 设计目标

1. **补全流程闭环**：从「能跑通」到「经得起追问」——改派、返工、挂起、合并、升级处置都有正经路径；
2. **强化跨模块集成**：座位下架/恢复精确到「座位」粒度，而不只是「房间」粒度；
3. **全过程可追溯**：每个动作都留痕，能回答「这张工单经历了什么」；
4. **不破坏既有契约**：M1/M2 的 16 条测试必须保持绿色，前端已有页面只做增量改造。

设计原则：**加字段不加表地优先，必须加表时只加一张**（事件表），避免为课程项目引入过重模型。

## 2. 状态机设计

### 2.1 状态集合

| 状态 | 含义 | 是否终态 | 座位是否下架 |
|---|---|---|---|
| `reported` | 已上报，待派单 | 否 | 是（若为 space/seat 类型） |
| `dispatched` | 已派单，待接单 | 否 | 是 |
| `in_progress` | 维修中 | 否 | 是 |
| `on_hold` | 挂起（等配件/等外部） | 否 | 是 |
| `completed` | 完工待验收 | 否 | 是（验收前不下架取消） |
| `accepted` | 验收通过 | **是** | 否（已恢复） |
| `cancelled` | 已取消 | **是** | 否（已恢复） |
| `merged` | 已合并到其它工单 | **是** | 不改变（由主线负责） |

新增 2 个状态：`on_hold`、`merged`。**不新增 `reopened` 状态**——返工复用 `in_progress`，用 `reopenCount` 计数表达，理由是状态越多前端分支越碎，而返工在语义上就是「重新维修中」。

### 2.2 流转规则

| 动作 | 允许的起始状态 | 目标状态 | 谁能做 | 座位联动 |
|---|---|---|---|---|
| 上报 | — | `reported` | 有 `workorder.report` | 下架（按对象粒度） |
| 派单 | `reported` | `dispatched` | `workorder.dispatch` | 无 |
| 改派 | `dispatched` / `in_progress` / `on_hold` | 状态不变 | `workorder.dispatch` | 无 |
| 开工 | `dispatched` | `in_progress` | 本人工单 + `workorder.handle` | 无 |
| 完工 | `in_progress` | `completed` | 本人工单 + `workorder.handle` | 无 |
| 挂起 | `dispatched` / `in_progress` | `on_hold` | 本人申请 → 派单员确认 | 无（保持下架） |
| 恢复 | `on_hold` | 回到 `preHoldStatus` | 派单员 | 无 |
| 验收通过 | `completed` | `accepted` | 上报人 + `workorder.accept` | **恢复** |
| 验收不通过 | `completed` | `in_progress` | 上报人 + `workorder.accept` | 不恢复（继续下架） |
| 取消 | `reported` / `dispatched` | `cancelled` | 上报人 / 派单员 | **恢复** |
| 合并 | `reported` | `merged` | 上报人 / 派单员 | 不改变 |
| 超时升级 | 非终态且未挂起 | 状态不变，`escalated=true` | 系统定时任务 | 无 |

非法流转一律抛 `ConflictException`（HTTP 409），越权抛 `ForbiddenException`（403），参数不合法抛 `BadRequestException`（400）——沿用现有异常风格。

## 3. 数据模型变更

### 3.1 `work_orders` 表新增字段

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `responseDeadline` | datetime NULL | NULL | 首响时限（now + `WORKORDER_RESPONSE_HOURS`） |
| `firstRespondedAt` | datetime NULL | NULL | 首次接单时间（开工时写入） |
| `onHoldSince` | datetime NULL | NULL | 进入挂起的时刻 |
| `totalHoldMinutes` | integer | 0 | 累计挂起分钟数，用于顺延解决时限 |
| `preHoldStatus` | varchar NULL | NULL | 挂起前的状态，用于精确恢复 |
| `reopenCount` | integer | 0 | 返工次数 |
| `mergedIntoId` | integer NULL | NULL | 合并后指向的主线工单 id |
| `escalated` | boolean | 0 | 是否处于升级待处理状态 |
| `resolutionNote` | text | '' | 维修说明（完工必填） |
| `photos` | text | '' | 现场照片，JSON 数组字符串（最多 3 项） |

保留 `slaDeadline` 作为**解决时限**，语义不变但计算方法改为「基准时间 + 时长 + 挂起顺延」，以兼容既有测试与前端。

### 3.2 新表 `work_order_events`

```
id            主键
workOrderId   工单 id（索引）
type          reported|dispatched|reassigned|started|completed|accepted|rejected|hold|resumed|cancelled|merged|escalated
fromStatus    变更前状态（NULL 表示创建）
toStatus      变更后状态
operatorId    操作人 id（系统为 NULL）
operatorName  操作人姓名快照（防用户改名后追溯失真）
note          备注（改派原因、返工原因、挂起原因等）
createdAt     发生时间
```

设计取向：**事件表只追加不修改**，作为工单的「黑匣子」。不做 CQRS、不做事件溯源（重放重建状态），只用它做展示与审计，保持课程项目可控。

### 3.3 `SeatStateService` 扩展

现有方法均为房间粒度（`setMaintenance(spaceId, ...)` / `restoreAfterMaintenance(spaceId, ...)`）。新增座位粒度方法，**保持向后兼容**：

```ts
/** 单个座位下架；已被下架时返回 false（幂等） */
setSeatMaintenance(seatId: number, workOrderId: number, operatorId: number | null, reason: string): Promise<boolean>

/** 单个座位恢复；非维修中状态直接返回 false */
restoreSeatAfterMaintenance(seatId: number, workOrderId: number, operatorId: number | null, reason: string): Promise<boolean>
```

内部复用私有 `apply()`，因此 `SeatStatusLog` 的 `refType='work_order'`、`refId=工单id`、`source='M3'` 自动保持一致，无需改日志表。

## 4. 接口设计

### 4.1 新增端点（不修改既有端点行为）

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/m3/work-orders/:id/reassign` | `workorder.dispatch` | 改派，body `{ assigneeId, reason? }` |
| POST | `/m3/work-orders/:id/hold` | `workorder.handle` | 申请挂起，body `{ reason }` |
| POST | `/m3/work-orders/:id/resume` | `workorder.dispatch` | 恢复，body `{ note? }` |
| POST | `/m3/work-orders/:id/merge` | `workorder.report` | 合并，body `{ targetId, reason? }` |
| GET | `/m3/work-orders/:id/events` | 单访问控制同详情 | 时间线 |
| GET | `/m3/work-orders` | 按角色过滤 | 统一列表，支持筛选分页 |
| GET | `/m3/work-orders/stats` | `workorder.stats` | 统计口径见 §8 |

### 4.2 变更的既有端点（向后兼容）

| 端点 | 变更 | 兼容性 |
|---|---|---|
| `POST /m3/work-orders` | 增加可选 `mergeIntoId`；检出重复未完结工单时返回 409 并带 `conflictWorkOrderNo` | 不传新参数时行为不变 |
| `POST /:id/accept` | 增加可选 `result: 'pass' \| 'fail'`，默认 `pass`；`fail` 时 `rating` 忽略 | 老调用方不传即通过，行为不变 |
| `POST /:id/complete` | 增加必填校验 `resolutionNote`（≥5 字） | **有破坏性**：前端需同步，故放在二期并与前端一起改 |
| `GET /pending` | 增加 `escalated=true` 过滤 | 不传时行为不变 |

### 4.3 响应结构约定

列表接口统一返回 `{ items, total, page, pageSize }`；既有的 `mine / pending / assignments` 保持返回数组，**不改**，新增的 `GET /m3/work-orders` 用新结构。

## 5. 权限与种子数据

新增权限码：

| 权限码 | 名称 | 授予角色 |
|---|---|---|
| `workorder.handle` | 工单处理 | `maintenance` |
| `workorder.accept` | 工单验收 | `student`、`teacher`、`ops`、`admin` |
| `workorder.manage` | 工单管理（合并/强制取消） | `ops`、`admin` |
| `workorder.stats` | 工单统计 | `ops`、`admin` |

种子脚本需保持幂等：已有权限码按 `code` upsert，角色权限按角色重建映射（先删后插或按集合差量），不得产生重复行。

新增系统配置（`system_configs`）：

| Key | 默认 | 说明 |
|---|---|---|
| `WORKORDER_RESPONSE_HOURS` | 4 | 首响时限 |
| `WORKORDER_MAX_REOPEN` | 3 | 最大返工次数 |
| `WORKORDER_HOLD_MAX_DAYS` | 7 | 挂起最长天数 |

## 6. 迁移方案

新增迁移文件：`backend/src/database/migrations/1780000001000-m3-work-order-enhance.ts`

- **up**：
  1. 逐列 `ALTER TABLE work_orders ADD COLUMN ...`（SQLite 与 PG 均支持 ADD COLUMN，避免整表重建）；
  2. `CREATE TABLE work_order_events` + 索引 `IDX_wo_events_workOrderId`；
  3. `CREATE INDEX IDX_work_orders_status` 加速列表与定时任务查询。
- **down**：
  1. `DROP TABLE work_order_events`；
  2. 删除新增列（PG 直接 `DROP COLUMN`；SQLite 3.35+ 支持，验证后启用，否则 down 只删表不删列并注明）；
  3. 索引删除。
- 时间戳命名沿用现有 `1780000000000` 顺序递增，保证执行顺序确定。
- **禁止**直接改 `1780000000000-init-schema.ts`，已应用的迁移不可修改。

## 7. 测试计划

新增测试文件 `backend/test/m3-work-order-enhance.spec.ts`（集成测试，内存 sqljs），至少覆盖：

| # | 用例 | 断言要点 | 破坏验证方法 |
|---|---|---|---|
| 1 | 单座位报修只下架该座位 | 该座位 maintenance、同房间其他座位 available | 把 `setSeatMaintenance` 换成整房间方法，测试应失败 |
| 2 | 重复下架幂等 | 第二次上报返回 409，`SeatStatusLog` 条数不变 | 去掉冲突检测，测试应失败 |
| 3 | 时间线完整性 | 5 步流转恰好 5 条事件，顺序正确 | 注释掉任一事件的写入，测试应失败 |
| 4 | 改派 | assignee 变更、原维修员操作 403、事件记录原维修员 | 不校验原维修员，测试应失败 |
| 5 | 验收不通过返工 | 状态回 in_progress、座位仍 maintenance、`reopenCount=1` | 让返工时恢复座位，测试应失败 |
| 6 | 返工次数上限 | 第 4 次不通过被拒绝（409） | 去掉上限判断，测试应失败 |
| 7 | 挂起暂停 SLA | 挂起 2h 后，`slaDeadline` 顺延 2h；定时任务跳过 on_hold | 去掉顺延逻辑，测试应失败 |
| 8 | 合并 | 合并单状态 merged、座位状态不变、主线验收后只恢复一次 | 合并单也触发下架，测试应失败 |
| 9 | 权限 | 无 `workorder.handle` 调 start 返回 403 且无事件新增 | 去掉权限装饰器，测试应失败 |
| 10 | 升级处置 | 超时后 `escalated=true`、进入升级列表、双人通知 | 只加层级不置标记，测试应失败 |
| 11 | 双时限 | 首响 3h 达标 / 5h 超时判定正确 | 判定条件写反，测试应失败 |
| 12 | 回归 | 既有 16 条测试全绿 | — |

测试数据通过 `createSpaceWithSeats` 一类的辅助函数构造，禁止 mock 掉被测 Service。

## 8. 统计口径（M3-18）

| 指标 | 定义 |
|---|---|
| 工单量 | 指定时间窗内创建且状态 ≠ merged 的工单数 |
| 完工率 | `accepted + completed` 数 / 总工单数 |
| 平均首响时长 | `firstRespondedAt - createdAt` 的均值，仅统计已首响工单 |
| 平均解决时长 | `acceptedAt - createdAt - totalHoldMinutes`，**扣除挂起时间** |
| SLA 达标率 | 首响与解决均未超时的工单数 / 已关闭工单数 |
| 返工率 | `reopenCount > 0` 的工单数 / 已关闭工单数 |
| 空间故障排行 | 按 `spaceId` 分组计数，降序取前 10 |

口径必须在接口返回中附带说明字段（`definitions`），避免口径歧义。

## 9. 分期实施计划

| 期次 | 内容 | 交付物 | 预估工作量 |
|---|---|---|---|
| **一期（P0）** | M3-07、08、09、10、11、12 | 迁移脚本、事件表、座位粒度、改派、返工、权限、升级处置 + 9 条测试 | 主要工作量所在 |
| **二期（P1）** | M3-13、14、15、16、17 | 双时限、挂起、合并、列表筛选、维修记录 + 前端改造 | 中等 |
| **三期（P2）** | M3-18 | 统计接口 + D 层统计页 M3 区块 | 较小 |

每期独立提交、独立合并请求，保证可回滚。一期完成前不动前端，避免前后端同时变更导致联调困难。

## 10. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| SQLite 的 `ALTER TABLE` 限制（不支持部分列变更） | 迁移失败 | 只做 ADD COLUMN，不改既有列类型；down 谨慎处理并实测 |
| `on_hold` 引入后定时任务误判 | 挂起工单被反复升级 | 定时任务查询条件显式排除 `on_hold`，并加测试 |
| 前端 `complete` 增加必填项 | 老前端报 400 | 一期不动前端；二期前后端同步改，先加后端可选、前端上线后再收紧 |
| 事件表写入遗漏 | 追溯断链 | 所有状态变更收敛到 Service 内的单一 `transition()` 私有方法，禁止在 Controller 写业务状态 |
| 与 M1 组对 `SeatStateService` 的改动冲突 | 合并冲突 | 新增方法而非修改既有方法；改动前在组内同步，必要时提 ADR 补充 |
| 返工无限循环 | 工单卡死 | `WORKORDER_MAX_REOPEN` 上限 + 超限升级人工介入 |
| M3 组同时承担 D4 通知 / D5 审计（ADR-0004 新分工） | 一期工作量显著上升，可能拖慢 P0 | 先按 ADR-0004 时间盒交付两子域的接口 + 最小实现 + 契约测试；M3 的派单/升级/返工通知与事件时间线正好是这两个子域的首个消费场景，可合并实现而非另起炉灶 |

## 11. 评审要点（请组长/M1 组确认）

1. `SeatStateService` 新增座位粒度方法，M1 组是否同意该方法签名与语义；
2. `on_hold` 状态是否影响 M1 座位列表展示（挂起期间座位保持下架，会长时间不可预约）；
3. 完成时限默认值（首响 4h、解决 48h）是否符合校园实际；
4. 一期是否按本文档范围冻结，不再追加需求。
